# Saas-gestionEmp — virtual back office for entrepreneurs

## Product context

A SaaS that gives a solo founder a virtual back office: AI agents answer legal,
accounting and HR questions, draft documents and emails, and help run client
follow-up, invoicing and legal deadlines.

Target jurisdictions, in order of priority: **Cameroon**, then the rest of
Africa, then Europe. Legal, tax and labour content therefore starts with the
law applicable in Cameroon (national law plus the regional OHADA and CEMAC
frameworks). Never assume French law or the euro by default.

The product backlog has 29 stories in 7 modules, delivered over 8 sprints:

| Module | Scope |
|---|---|
| M1 Core and access | Secure login, GDPR export / erasure |
| M2 Agent control | Single entry point, human validation, audit log, confidence level, autonomy, cost tracking, referral to a human professional |
| M3 Legal agent | Legal questions with sources, contract drafts, labour law |
| M4 Accounting and finance | Accounting / tax questions, invoices, unpaid invoices, cash flow |
| M5 Client management | Client records, interactions, follow-ups, agent-drafted emails, pipeline, contact import |
| M6 Employee management | Employee files, leave requests, HR documents, onboarding |
| M7 Founder steering | "My day" dashboard, legal obligations calendar, calendar / mail sync |

Explicitly out of scope: agents filing tax returns, fully autonomous agents on
financial or legal actions, a native mobile app, payroll.

### Product rules that shape the code

- **Human in the loop.** An agent never executes an action with an external
  effect (sending an email, issuing a document) on its own. It creates a
  `ProposedAction` that the founder validates or rejects.
- **Every agent action is logged** in an append-only audit log.
- **Every agent answer carries** its sources, a disclaimer and a confidence
  level. Low confidence leads to a referral to a human professional. The
  professional is not a user of the system.
- **Tenant isolation.** A company never sees another company's data.
- **Jurisdiction-aware.** A company has a country. Legal sources, obligations,
  invoice mandatory mentions, tax rates and currency depend on it, so none of
  them is hard-coded.

Actors: Founder (main user), Employee (leave requests), AI agents, external
services (email, calendar), scheduler (alerts and reminders).

## Backend architecture

One Django app per business domain:

| App | Main models | Module |
|---|---|---|
| `core` | abstract `BaseModel`, `CompanyOwnedModel`; health endpoint | shared |
| `accounts` | `Company`, `User`, `Membership`, `DataRequest` | M1 |
| `agents` | `Agent`, `Conversation`, `Query`, `Answer`, `Source`, `LegalReference`, `ProposedAction`, `AuditLogEntry`, `UsageRecord` | M2, M3 |
| `crm` | `Client`, `Interaction`, `FollowUp`, `Opportunity` | M5 |
| `billing` | `Invoice`, `InvoiceLine`, `Payment`, `CashMovement` | M4 |
| `documents` | `Document` | M3, M6 |
| `hr` | `Employee`, `LeaveRequest`, `OnboardingPlan`, `OnboardingStep` | M6 |
| `planning` | `Obligation`, `Alert`, `ExternalConnection` | M7 |

Rules:

- **Dependency direction.** Business apps may import from `accounts` and
  `agents`. `accounts` and `agents` never import from business apps.
- **Custom user model** (`accounts.User`, login by email) set in
  `AUTH_USER_MODEL` before the first migration.
- **A user can belong to several companies.** `Membership` links `User` and
  `Company` and carries the role (founder, employee). Every request runs in the
  context of one active company, named by the `X-Company-ID` header, and permissions are checked against the
  membership for that company, never against the user alone.
- **Tenant scoping in one place.** Business models inherit from
  `core.models.CompanyOwnedModel`, and their views use
  `accounts.tenancy.CompanyScopedMixin`, which filters on the active company
  and sets it on created rows. Never filter on the company by hand in a view.
- **Legal knowledge is data, tagged by jurisdiction.** `LegalReference` holds
  the curated texts the agents cite (country or regional body, source, date),
  and `Obligation` templates are per country. `Company.country` selects which
  ones apply. Money fields always come with a currency (XAF first).
- **Cash flow is entered manually** (`CashMovement`); no bank integration.
- **Thin views, logic in services.** Each app has `models.py`,
  `serializers.py`, `views.py`, `urls.py`, `services.py` (writes and business
  rules), `selectors.py` (non-trivial reads) and `tests/`. A view validates
  input, calls a service, returns a response.
- **`ProposedAction` is a strict state machine**: `pending` → `approved` /
  `rejected` → `executed`. Transitions go through services only, and each one
  writes an `AuditLogEntry`.
- **No direct LLM SDK call in business code.** Calls go through a provider
  interface in `agents`, so the model can be swapped and tests use a fake.
- **"My day" has no model.** It is a read over follow-ups, obligations, pending
  actions and overdue invoices.
- Follow Django conventions before adding abstraction. No repository layer, no
  entities separate from the ORM.

## API conventions

- All routes under `/api/v1/`.
- Deny by default: `IsAuthenticated` globally, each view declares its
  permissions explicitly.
- Paginated list endpoints.
- The OpenAPI schema is the contract with the frontend. Define or update it
  first; the frontend generates its TypeScript types from it.
- Expose UUIDs, not sequential ids, in URLs.

## Code conventions

- **English** for code, identifiers, comments, commits and branch names.
- **French and English** for the interface and agent answers, following the
  user's language. No user-facing string is hard-coded: use Django's
  translation functions on the backend and an i18n library on the frontend.
  API error codes are stable identifiers, translated by the client.
- Configuration through environment variables. No secret in git.
- Tests focus on services, permissions and tenant isolation. LLM calls are
  always faked in tests.
- Prompts live in code and are versioned like code.

## Git workflow

- `main` is protected and always deployable: no direct push, one review, CI
  green.
- One short-lived branch per story: `feature/US-03-client-record`,
  `fix/...`, `chore/...`. Merge within a day or two.
- Small pull requests, story id in the title.
- Migrations: rebase on `main` before running `makemigrations`; never edit a
  migration that is already merged.
- Commit or push only when asked.
